# BestChoice Agent 工作规则

## 1. 目标推进方式

- 以 `goal.md` 为当前实施目标，但不能机械执行旧方案。
- 开发过程中如果真实数据、回测结果、性能瓶颈或用户反馈证明原方案不合理，必须更新 `goal.md` 后继续推进。
- 最终目标允许在开发中演进，但演进必须服务于用户的真实使用目标：
  - 选股列表更准确。
  - 明细解释更贴近实际策略。
  - 回测口径更接近真实成交。
  - 页面响应和计算资源可控。
- 发现实现路径与最终使用目标冲突时，先修正目标文档，再改代码；不能为了贴合旧文档保留明显错误的设计。
- 调整目标时要保留原因：
  - 发现了什么实际情况。
  - 原方案哪里不合适。
  - 新目标如何更符合最终使用场景。
- 不把“已写代码”当成完成依据，必须以可运行结果、接口返回、图表表现和测试结果为准。
- 每次阶段性完成后，要把“实际已验证的行为”和“仍未完成的风险”同步回 `goal.md` 或 `analysis/` 审计报告，避免下一轮从过期假设继续。

## 2. 并发原则

- 外部算力约束：
  - 除非用户在当前对话中明确说明可以使用 GCP，否则 BestChoice 任务一律只在本地运行。
  - 不主动启动、停止、监控或占用任何 GCP VM / GCS / 远端训练任务；`chunkymonkey` 相关 GCP 资源优先服务其主项目。
  - 本地任务耗时很长时，只能先向用户说明情况并等待明确授权，不能自行切到 GCP。

- 能并发的任务要并发：
  - 文件检索、代码阅读、状态检查可以并行。
  - 互不写同一文件的分析/验证可以并行。
  - 长时间回测运行时，可以同时做不依赖该结果的代码审计或文档更新。
- 并发是默认优化手段，不是可选装饰：
  - 只读检查优先用并发。
  - 多个独立 smoke test 可以并发。
  - 多个公式缓存可分批并发，但必须遵守 CPU 和服务响应约束。
  - 服务接口验证和离线审计可以错峰并行，避免互相争用数据库写锁。
- 并发必须有上限：
  - 全量回测是 CPU 密集任务，不能一次性启动所有策略。
  - 统一股票池预热默认最多并行 2 个策略，避免 `/api/status`、页面加载和健康检查被拖死。
  - 后台预热只预热统一股票池需要的策略；旧的单策略/MACD 参数组按需计算，不能抢占主入口资源。
  - 如果真实运行发现服务响应变慢，优先降低并发而不是继续堆线程。
- 并发执行后必须汇总结果：
  - 不能只看最先完成的任务。
  - 任一并发验证失败，都要回到修复闭环。
  - 不能用其他通过项掩盖一个失败项。
- 不能并发的任务不要并发：
  - 同一文件的多个补丁不能并行。
  - 依赖前一步结果的修复不能提前猜测实施。
  - 涉及缓存失效、服务重启、数据库写入的操作要串行。
- 如使用子代理：
  - 只在用户允许并行或明确要求时使用。
  - 子代理优先做只读分析、独立验证或不冲突的代码改动。
  - 主代理负责整合、测试和最终判断。

## 3. 开发闭环

每个实质改动都要形成闭环：

1. 明确要修复或新增的行为。
2. 修改代码。
3. 运行最小验证：
   - `python -m py_compile ...`
   - smoke test
   - 关键函数真实数据抽查
   - 必要时启动服务查接口
4. 如果验证失败，立即修复，不把问题留给下一轮。
5. 记录仍未覆盖的风险。

## 4. 数据和回测口径

- 回测、当前预测、走势图必须共用同一套交易执行模型。
- 买卖价格默认使用可成交 VWAP，不使用简单收盘价替代。
- 必须处理：
  - T+1 买入。
  - 停牌。
  - 涨停买入阻塞。
  - 跌停卖出阻塞。
  - 一字板。
  - 买卖顺延。
- 图表红绿持仓填充只能来自实际买入日到实际卖出日，不能来自金叉/死叉区间。
- 当前候选/今日推荐不能只看是否命中公式，必须结合：
  - 是否处于买入窗口。
  - 历史胜率。
  - 均收益。
  - 均回撤。
  - 有效性评分。
  - 成交可行性。

## 5. 策略设计原则

- MACD 和通达信公式都作为统一股票池的策略信号来源。
- 不再把每个公式作为最终用户主列表。
- 单公式视图可以保留为“策略研究/参数寻优/调试”用途。
- 最终日常主入口应是统一股票列表：
  - 今日推荐。
  - 买入窗口。
  - 持仓观察。
  - 全部股票。
- 股票详情页按股票聚合展示所有策略卡片，而不是只展示当前单策略。
- 多策略共振优先，但高质量单策略信号也可以进入推荐。

## 6. 公式策略实施规则

- 通达信公式必须转成 bestchoice 本地逐日信号，不能只依赖最新筛选表。
- 每个公式都要独立回测、独立参数寻优、独立生成买卖点。
- 公式信号不默认围绕 MACD 金叉解释，除非公式本身包含 MACD 条件。
- 参数探索不局限于用户原始公式固定参数，但必须记录探索范围和结果。
- 发现公式过严或过松时，用真实样例和全市场结果调整默认参数，并写入 `goal.md` 或分析报告。

## 7. UI 规则

- UI 设计与现有风格保持一致，不引入突兀的新视觉体系。
- 改 UI 前先确保后端语义正确。
- 旧功能不能无说明破坏：
  - 股票列表。
  - 股票详情。
  - 三张图。
  - 打印。
  - 自动数据健康检查。
- 无数据、无样本、样本陈旧必须在界面明确提示，不能展示空白图。

## 8. 验收规则

完成前必须做审计，不能凭感觉结束。

审计清单至少包括：

- `goal.md` 的显式要求是否有对应实现。
- 新增或修改的接口是否能返回真实数据。
- `301511`、`301658`、`688700`、`002718` 等关键样例是否检查。
- 语法检查和 smoke test 是否通过。
- 缓存是否因 schema/执行模型/公式逻辑变化而失效。
- 是否生成必要的 `analysis/` 审计产物。

只有审计确认无剩余必需项时，才能认为目标完成。
