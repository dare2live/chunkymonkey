# 数据获取 v2 设计 — 从补丁到信道治理 (2026-06-12 深夜, 用户授权全局重设计)

> 触发: 用户 "数据获取一直出问题, 第一性原理看是否不再沿用最开始的方法/渠道, 重新设计而不是打补丁"。
> 状态: 设计稿, 待对抗评审 → 用户渠道决策 → 实施 (排 chain9 收尾后)。

## 0. 第一性三问

1. **真相源是什么?** 数据正确性的真相源 = 官方数据语义 (limit/offset/行数/字段)。当前链路里
   横着一个第三方代理网关 (jiaoch.site), 它对官方语义的偏离 (无视分页参数/截断/空响应) 是本周
   ~70% 数据事故的根源。**代理网关不是渠道, 是噪声源。**
2. **能不能更简单?** 现架构 sync_runner (registry 驱动/水位/失败队列/drain/样本契约/弹仓) 是
   本周实战验证有效的, 不重写。病变器官只有两个: (a) fetch 层把网关行为当常数 (page_limit/
   min_rows 静态硬编码, 网关一变就过时) (b) 渠道本身不可预期。**置换器官, 不推倒大楼。**
3. **判断规则写在哪?** 信道行为契约、行数带、预算 — 全部进 yaml, 运行时实测校准, 不再人工标定。

### 限流定层结论 (2026-06-13, 对照本地官方文档镜像 + 代理商原话)

**撞墙的是代理 jiaoch.site 的账户级反刷量墙, 不是 TuShare 官方积分配额。** 铁证四条:
1. 官方日上限按**接口**算 (2000 档 10 万次/个 API; cyq 类特色 5000 档单接口 1 万次/天), 从无账户全局共享计数器; 实测 dc_member+trade_cal+daily 三接口**同时**报上限 = 全局计数器, 官方无此机制。
2. 官方 doc_id=290 表一: **5000+ 积分常规数据无日上限, 10000+ 常规无上限+特色数据300次/分钟**。当日烧配额的 8 个接口 (daily/trade_cal/dc_member/dc_index/daily_basic/fina_mainbz/top_inst/suspend_d) **全是常规数据** (特色数据白名单只有: 盈利预测/每日筹码和胜率/筹码分布/券商月金股), 真 10000 积分一个都不该日封顶。
3. trade_cal (2000 积分基础接口) 被封顶是决定性反证 — 5000+ 档它无上限。
4. 报错串 "今日请求已达上限，请明天再试！" 在整个官方文档镜像命中 **0 次** (官方限流措辞是"每分钟最多访问该接口X次"); 代理商自述 = "请求过多会被系统认为攻击" → 代理自有反刷量层。

**处置**: 官方直连 5000 积分 (¥500/年) 根治日封顶 (常规数据全无上限); cyq 特色数据线需 10000 积分 (¥1000/年)。信道 channel-agnostic, 改 TUSHARE_HTTP_URL 零代码切换。在切换前, 熔断 (#9) 防止反刷量被逐日续戳放大。本地官方文档镜像: `/Users/dp/Documents/M/stock/tushare/tushare.pro/document/`。

**已切换 (2026-06-17)**: 弃用 jiaoch.site (反刷量墙封死 stk_surv 等), 改 **tinyshare** 代理 (`import tinyshare as ts; ts.set_token(授权码); ts.pro_api()`, 自带网关无需 _DataApi__http_url; 授权码进 .env)。实测解封: stk_surv 机构调研单日 316 行、daily/moneyflow 正常。**tinyshare 限流 (用户 2026-06-17): 单接口 120 次/分钟, 多接口 200 次/分钟, 并发上限 2** (旧 tushare 150/200); 瞬态限流退避几分钟即恢复, sync_runner `_is_transient_ratelimit` + 专用更长退避已实现 (非"当日墙"不停链)。`_pro_api` owner = `backend/services/data_sources/sources/tushare.py`。

## 2. 渠道决策 (需用户拍板的唯一一项)

**结论先行: 真金白银项目的数据地基不该建在行为不可预期的代理网关上。**

| 选项 | 正确性 | 成本 | 判定 |
|---|---|---|---|
| A. 官方 tushare 直连 (api.tushare.pro 自有积分) | 文档语义可依赖, 限频透明 (积分=频次), 分页规范 | 积分年费: 2000 分档约数百元/年, 5000 分档约 ¥1k-2k/年 (以官网实价为准; 本项目 22+25 域绝大多数 ≤6000 分) | **推荐主信道** |
| B. 现代理网关 | 本周病理全记录在案 | 已付 (沉没) | 降级为备援信道, 套病理防护后用于量大低敏回填 |
| C. 双网关混用 | 两套病理面 | 复杂度翻倍 | 拒绝 ("不用全用, 容易混" 同理) |
| D. 换数据商 (Wind/聚宽/米筐) | 好但封闭/贵一个量级 | ¥万级/年 | 拒绝 (超出需求) |

**建议: A 主 + B 备 (B 仅在 A 限频不够时给历史回填分流, 且必须过同一套响应验收)。**
若用户暂不开通官方积分: B-only 也可运行, 但本设计的全部防护 (信道契约探针/响应验收/预算熔断)
成为必需而非可选 — 即"带着病人活下去"的完整护理方案。

## 3. 架构: 三层置换 (保 registry 大盘, 换 fetch 器官)

```
sync_runner (registry/水位/队列/drain — 不动)
   └── AcquisitionChannel  (新, services/data_sources/channel.py)
        ├── 行为契约探针   ── 启动自检: limit/offset 语义实测 (3 发) → 信道模式判定
        ├── 节奏与预算     ── token bucket 实测校准 + 调用预算账本 + 时段熔断
        └── 响应验收 (统一) ── 行数带(自动标定)/截断签名/重复页/grain 重复率
```

### 3.1 信道行为契约探针 (根治 #1/#2/#5)

每信道每会话首次使用时 3 发探针 (已知日 + limit/offset 组合) 实测判定信道模式:
`paged` (官方语义) / `full_payload` (无视参数返全量) / `hard_cap` (截断, 上限=N)。
模式写入运行时信道状态, fetch 策略按模式分派 — **网关行为变更当天被探针发现,
而不是烧 4300 发后人肉诊断**。探针结果落 `data/reports/channel_probe_*.json` 留证。

### 3.2 节奏与预算 (根治 #3/#4)

- token bucket: 速率初值来自 yaml, 运行时按实测响应延迟自适应 (晚高峰自动降速)。
- **调用预算账本**: 每个链/任务启动时申报预算 (chain9 ≈ 9.7k), 信道计数, 超预算 20%
  熔断停链 + 告警 — 白烧类事故的硬上限。
- 吞吐熔断: 滑动窗实测吞吐 < 申报需求的 1/3 持续 15 分钟 → 暂停并告警 "改期建议"
  (替代今晚的人工定点终止)。

### 3.3 响应验收统一层 (根治 #2/#6)

每批响应过四道, 全部集中一处 (不再散在 runner 各分支):
1. **行数带自动标定**: min/max 带 = 同域 raw 表近 N 个同月历史分位 (p5..p99x1.5),
   分年自适应 — 根治 min_rows 静态标定漂移 (2019 年 3700 只 vs 2026 年 5512 只)。
   无历史时回退 registry 静态值 (冷启动)。
2. 截断签名: 行数 == 信道 hard_cap 或整倍数 pin → fail-closed。
3. 重复页签名: 已实现 (相同页守卫), 移入本层。
4. grain 重复率: 批内按 grain 去重率 < 99.9% → 可疑入队。

### 3.4 不做的 (奥卡姆)

- 不重写 sync_runner / registry / drain / 水位 / 队列 (本周实战已验证)。
- 不做多信道自动路由/负载均衡 (两个信道, 人工指定主备即可)。
- 不做异步化改造 (吞吐瓶颈在对端限频, 不在本端并发)。

- 感知死: 探针结果 30 天无更新 (信道模式从未复测) = 设计退化为新的"假设固化"。
